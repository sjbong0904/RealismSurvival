# 전수 검토 01 — 커스텀 모드 기능 완성도

검토일: 2026-10-21  
검토 기준: 00번에서 정한 `runClient` 기본 개발 구성.  
범위: RS 코어 `src/main/java` 202개 파일, `rs-medicine` 15개 파일, 해당 모드 리소스·메타데이터·API 문서. 외부 모드와의 게임플레이 밸런스 및 전체 플레이 흐름은 이번 회차에서 판단하지 않는다.

## 요약

커스텀 코드의 핵심 시스템은 **프로토타입을 넘어서 기능 단위가 갖춰진 상태**다. 코어는 서버 권위형 플레이어 상태, 데이터팩 기반 갈증/단열/음료 설정, 등급 물·처리 블록·용기 변환, HUD, 설정, 선택 모드 호환 지점을 갖췄다. `rs-medicine`도 별도 모드 ID, 의약품·효과 등록, 사용 처리, 치유·해독, 상태이상 아이콘과 한국어 리소스를 구현했다.

정적 구조 검토에서 즉시 고쳐야 한다고 확정할 런타임 결함은 찾지 못했다. 다만 API를 애드온 계약으로 내세우는 구조와 실제 배포 단위 사이에 아직 정리되지 않은 경계가 있다. 이 보고서는 코드 읽기 기반이며 빌드와 게임 실행은 하지 않았다.

## 기능·구조 현황

| 영역 | 확인된 구현 | 코드 구조상 평가 |
|---|---|---|

| 확장 계약 | `SurvivalApi`, `WaterApi`, 태그 상수, 다수의 생존·물 계산 이벤트, JSON 데이터 조회 facade | 모드 간 연결점을 상당히 제공한다. API 패키지 밖 구현 타입 노출은 아래 발견사항 참조. |
| 물 시스템 | 품질 레지스트리, 액체·병·양동이·얼음, 채우기/변환/가마솥/스펀지/수생 생물 처리, 필터·증류기 | 실제 바닐라 물 상호작용까지 폭넓게 다뤄 완성도는 높지만, Mixin/이벤트 경계가 많아 회귀 부담도 크다. |

| rs-medicine | 회복·해독·상태 대응 아이템, 일부 몹/피격별 발병, 5% 추가 효과, 아이콘 및 `en_us`/`ko_kr` | 사용 가능한 수직 기능 묶음은 완성되어 있다. 확률·효과 세기 적절성은 02번/04번 등 게임 밸런스 회차로 넘긴다. |
| 확인 코드 | 코어 GameTest 함수 18개가 `SurvivalGameTests`에 등록되어 있음. Addon 전용 GameTest는 확인하지 못함. | 회귀 검증의 기반은 있으나 애드온과 일부 통합 기능의 자동 검증 범위가 불명확하다. 이번에는 테스트를 실행하지 않았다. |

## 발견사항 및 수정 방향

### 01-1 — 애드온 API가 구현 패키지 타입에 직접 묶임 (P1, 계약 안정성)

`SurvivalApi.getData()`는 `component.SurvivalData`를 반환하고, `SurvivalDataAccess`는 `data.BiomeThirstProfile`, `data.DrinkDefinition`, `data.InsulationDefinition`을 그대로 반환한다. 즉, 애드온 작성자는 facade를 사용해도 내부 구현 패키지 타입에 컴파일 의존한다. `docs/ADDON_API.md`는 `SurvivalData`가 임시 예외라고 적지만, 나머지 데이터 record도 같은 경계 문제를 갖는다.

**수정 방향 제안:** API 계약에 노출할 타입을 `api` 아래의 공개 DTO/record로 정하고, 구현 데이터 타입에서 변환한다. 또는 API facade에 `getThirst`, `setThirst`, `getDrinkDefinition`처럼 고정된 조회 계약을 제공한다. 0.x 동안 변경을 허용하더라도 어느 패키지와 타입이 지원 계약인지 문서와 SemVer 정책을 일치시킨다. 기존 API 이용자 호환성을 확인하지 않고 타입 이동부터 적용하지 않는다.

### 01-2 — `rs-medicine`의 독립 빌드 산출물이 확인되지 않음 (P1, 배포 경계)

`build.gradle`에는 `medicineAddon` 소스셋과 ModDev 런타임 모드 바인딩이 있지만, 확인된 빌드 구성에는 이 소스셋용 별도 JAR·게시 작업이 없다. 현재 설정은 개발 실행에서 코어와 애드온을 함께 로드하는 것을 지원하지만, 코어와 분리된 `rsmedicine` JAR로 재사용/배포할 수 있는 경로는 문서화·자동화되어 있지 않다.

**수정 방향 제안:** 모드팩 전용으로만 배포할지, 애드온 독립 JAR로 배포할지 먼저 결정한다. 독립 배포가 목표면 `rs-medicine`용 JAR 산출·메타데이터 검증·버전 결합 방식을 추가한다. 팩 내부 전용이면 그 점을 문서에 명시하고 소스셋 이름과 독립 공개 API 기대를 조정한다. 배포 완성도 판단은 13번에서 실제 산출물로 확정한다.

### 01-3 — 메타데이터 의존 버전 범위가 실제 지원 범위보다 넓어 보임 (P2)

코어는 NeoForge `[26.1.2.122,)`에 의존하지만, `rsmedicine` 메타데이터는 NeoForge `[26.1,)`, 코어 `[0.1.0,)`을 허용한다. 팩이 특정 26.1.2 조합만 지원한다면 로더가 메타데이터를 기준으로 더 낮거나 호환성이 보장되지 않은 조합도 허용할 수 있다.

**수정 방향 제안:** 독립 addon을 빌드하기로 결정하면 Minecraft/NeoForge/코어의 지원 범위를 실제로 검증한 버전 범위로 맞춘다. 호환 범위를 넓게 열 경우 각 범위가 실제 테스트된 것인지 구분해서 기록한다.

### 01-4 — 공개 전 자리표시자 식별자가 남아 있음 (P2, 출시 준비)

Java 패키지와 Maven group이 `com.example.realismsurvival`이다. `docs/VERSIONING.md`도 공개 전에 변경해야 한다고 이미 적어 두었다. 현재 내부 개발에서는 기능 장애가 아니지만, 외부 addon이 이 경로로 컴파일되기 시작하면 변경 비용이 커진다.

**수정 방향 제안:** 첫 공개 addon/API 계약을 고정하기 전에 고유한 역도메인 패키지·Maven group·저장소 주소를 확정하고 한 번에 이관한다. 결정과 이관은 13번 배포 검토에 기록한다.

### 01-5 — 핵심 물 동작이 다수 필수 Mixin에 걸려 있음 (P2, 유지보수 위험)

코어 Mixin 설정은 `required: true`, `defaultRequire: 1`이며 물 흐름·바이옴 강수/동결·블록·용기·수생 생물 상호작용에 다수의 필수 Mixin을 둔다. 이는 등급 물을 바닐라 세계와 맞물리게 하는 설계상 이유가 있지만, Minecraft/NeoForge의 내부 메서드 변경이나 충돌 Mixin에서 로딩 실패 가능성을 키운다.

**수정 방향 제안:** 현재 필수 여부를 무조건 낮추기보다, 각 Mixin에 목적과 필수성 기준을 문서화하고 물 시스템의 정상/경계 상호작용을 지원 버전마다 자동 검증한다. 핵심 기능이 깨진 채 조용히 진행되는 방식은 피하고, 선택 호환 Mixin(Sodium/Fish of Thieves)과 코어 필수 Mixin의 장애 처리를 분리한다.

### 01-6 — 의약품 애드온의 독립 회귀 검증 근거가 부족함 (P2, 검증 공백)

코어에는 갈증·온도·물 처리 중심 GameTest가 등록되어 있으나 `rs-medicine`에는 별도 GameTest가 확인되지 않았다. 애드온은 사용 시간 종료, 수량 감소, 피해 후 발병, 화염/동결 해제, 치유 우회 등 자체 동작이 있어 코어 테스트만으로 계약을 보장하기 어렵다.

**수정 방향 제안:** 빌드/검증 회차에서 최소한 아이템 1회 사용·치유량·상태 해제·발병 조건·코어의 자연 회복 배율과 독립된 회복을 검증하는 작은 테스트 묶음을 추가한다. 이는 아직 실행하거나 추가하지 않았다.

## 긍정적으로 확인된 설계

- 첨부 데이터는 불변 값 객체이며 서버에서만 변경하고 소유 클라이언트에 동기화한다.
- 클라이언트 전용 화면/HUD/렌더링 코드를 별도 엔트리 포인트로 분리했다.
- 데이터팩 리로드와 서버 설정을 통해 조정할 수 있어 수치 변경이 코드 수정에만 묶이지 않는다.
- 선택 모드 호환이 필요한 경우 Reflection/별도 Mixin 설정 등으로 경계를 분리하려는 패턴이 있다.
- 애드온은 코어 상태 API를 이용해 치유 배율 예외를 처리하므로 자연 회복 조정과 아이템 치유를 구분할 의도가 코드에 드러난다.

## 회차 결론

커스텀 모드는 플레이 가능한 기능 묶음을 갖췄으며, 현재 가장 큰 완성도 과제는 **새 기능 추가보다 계약/배포 경계와 검증 범위를 고정하는 일**이다. 우선 제안 순서는 (1) API 지원 타입을 확정, (2) `rs-medicine` 배포 형태 결정, (3) 그 결정에 맞춰 metadata와 테스트 전략 정리, (4) 공개 전 package/group 식별자 이관이다. 물/생존 동작의 품질 평가는 다음 02번에서 별도로 수행한다.
