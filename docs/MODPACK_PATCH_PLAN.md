- 작성일: 2026-10-21
- 기준: `MODPACK_REVIEW_00`–`14` 정적 검토 결과와 사용자가 채택한 수정 방향
- 목적: 세부 문제를 빠뜨리지 않고, 선행 결정·데이터 정본·저장 호환·사용자 흐름을 고려해 작은 패치 단위로 순서화
- 현 상태: **0–8단계 적용 완료, 자동 확인 통과(compile · GameTest 19/19 · 브리지 79/79 · ko_kr 누락 0), 실플레이 검증 대기.** 진행 기록: [MODPACK_PATCH_STAGE0.md](MODPACK_PATCH_STAGE0.md). 수동 회귀: [REGRESSION_CHECKLIST.md](REGRESSION_CHECKLIST.md). 보류: 1.5(D-11), 6.7–6.8·7.1 공개 직전 작업([MODPACK_RELEASE_PREP.md](MODPACK_RELEASE_PREP.md)), 7.4–7.5는 `/realism stats` 측정 후.

## 적용 원칙

1. 사용자가 채택한 방향을 수정 범위로 삼되, 평가가 양호했던 다이아 조기 노출·Oritech 단계 소개·BoP 태그 분류·레시피 원가 보존·NPC 명령 차단은 회귀 방지 항목으로 둔다.
2. 생성 원본과 산출물을 함께 고친다. FTB Quests는 생성 코드/카탈로그/퀘스트 데이터/언어 파일/목록 내보내기를 한 변경 묶음으로 취급한다. JAR와 데이터팩에 복제된 레시피는 정본을 하나 정한 뒤 생성·검증 절차를 둔다.
3. 플레이 경험이나 성능 결론이 필요한 수치는 임의로 고정하지 않는다. 먼저 의도와 기준을 문서화하고, 코드/데이터 변경 다음에 플레이·다인·프로파일링 확인을 붙인다.
4. 퀘스트 ID, attachment/`SavedData` 포맷, API 공개 계약, 외부 모드 지원 범위는 호환성 영향이 있으므로 각각 별도 패치로 나눈다.
5. 패치마다 변경 파일, 정적/자동 검증, 실제 플레이가 필요한 기준, 통과/보류를 진행 기록에 남긴다. 문서 수정을 코드 구현 완료로 간주하지 않는다.

## 우선순위 결정 기준

- **선행 결정**: 배포 프로필, 애드온 배포 단위/API 계약, 판매 가능 아이템과 가격 정책.
- **핵심 진행 P1**: 생존 수치의 설정 독립성, 필수 넵튜늄 RNG 관문, 실제 과제와 설명 불일치, 작물 계절 API 실패 일관성.
- **사용성/완성도 P2**: 퀘스트 문안·보상, 매입 GUI, 한국어 기본 적용, 미등록 아이템 가격 정책.
- **출시/확장 P2**: 서버 부하와 대규모 거래는 먼저 측정하고 문제가 확인되면 최적화한다.

## 병렬로 설계할 수 있지만 구현은 순서를 지킬 항목

- `08 문안/보상`과 `11 번역`은 4.2–4.6에서 퀘스트 원본이 확정된 뒤 번역/리소스팩 산출을 한다.
- `10 상점 GUI`와 `04 경제`는 가격·허용 아이템 정책(5.1)이 끝난 뒤 병렬 구현할 수 있지만, 거래 확정/동기화는 같은 서버 규칙을 사용해야 한다.
- `01 API`와 `13 배포`는 패치 중에는 세부 협의를 병행할 수 있으나 공개 ID/API 이동은 계약 결정 이후 한 번만 한다.
- 프로파일링, 월드 생성 거리, 실제 플레이 시간은 언제든 관측할 수 있지만, 수치 변경 전 기준값을 남기고 변경 후 동일 조건으로 다시 측정한다.

## 시작 제안

첫 실제 수정 묶음은 **0.1–0.3 결정표 + 1.1–1.4 생존 핵심 정합성**으로 시작한다. 1단계가 끝나면 세이브와 수치 밸런스를 먼저 확인하고 2–4단계로 넘어간다. 플레이 진행을 막을 수 있는 3.1 넵튜늄 첫 수급 대안은 초반 생존 패치와 병렬로 설계하되, C4 보상 변경은 4.5에서 퀘스트 전체 보상표와 함께 반영한다. 상점 계산대는 정책 설계 없이 GUI부터 만들지 않는다.
