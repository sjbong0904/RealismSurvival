# 전수 검토 12 — 멀티플레이·저장·권한·성능

- 검토일: 2026-10-21
- 범위: 커스텀 생존 데이터 저장/동기화, 월드 저장 데이터, 명령/상점 권한, 서버 틱 작업과 블록 엔티티, 서버 전용 로딩 구조
- 증거 수준: 코드 정적 확인. dedicated server, 재접속, 다인 동시 거래, 장시간 TPS/메모리 프로파일링 미실행.

## 요약 결론

플레이어 갈증/체온은 NeoForge attachment로 저장되고 소유 클라이언트에만 동기화되며, 관리자 조정 명령은 권한 등급으로 제한된다. 물 변환 상태와 신선수 고임 시각도 청크/차원 저장 데이터에 기록한다. 서버/클라이언트 코드 분리와 서버 권위 구조는 대체로 명시적이다.

실서버에서 확인해야 할 핵심 위험은 두 가지다. 첫째, 신선수 고임 추적 데이터는 차원별 장기 저장 Map이며, 주기 스캔 때 모든 추적 항목의 키 배열을 만들고 전체 항목을 훑는다. 플레이어 주변 청크 검사에는 예산이 있지만 누적 추적 항목 처리량에는 예산이 없다. 둘째, Q Shop/SG Economy 브리지는 플레이어별 40틱마다 리플렉션 기반 잔액 조회와 동기화를 수행하므로 동시 접속자 규모와 저장/패킷 영향 측정이 필요하다. 두 항목은 정적 코드만으로 실제 병목이라고 단정할 수 없다.

## 확인 결과

- `SurvivalAttachments.SURVIVAL_DATA`: Codec 직렬화, 사망 시 복사, 소유 클라이언트에만 sync. tick handler는 평가 결과가 달라질 때만 값을 기록해 동기화한다.
- 데이터팩 테이블: 서버가 로드한 불변 스냅샷을 payload로 클라이언트에 보낸다. 패킷은 서버→클라이언트 전용으로 등록되어 있다.
- 물 변환: 청크에 `WATER_CONVERTED` attachment를 저장한다. 구 청크는 차원별 대기 집합에 등록해 틱당 2청크씩 한 번 변환한다. 새 청크는 worldgen 단계에서 변환하도록 설계되어 있다.
- 신선수 고임: `FreshPoolDecayData`는 차원 `SavedData`로 좌표와 최초 관찰 game time을 저장한다. 플레이어 주변 최대 25청크 후보 중 설정된 예산만 스캔하지만, 추적 항목 전체 검사에는 별도 예산이 없다.
- 관리자 명령: `/realism get/set`은 GameMaster 권한 체크를 통과해야 한다.
- 공급소 직접 `qshop open` 차단은 CommandEvent에서 작동하며, NPC 우클릭이 기본 진입이다. `nearSupplyMerchant` 함수는 OP/크리에이티브 예외가 있으나 일반 상호작용 진입은 이 함수를 통하지 않는다.
- 통화 연결: 로그인 시 및 플레이어별 40틱 간격으로 SG 잔액을 Q Shop 잔액과 대조하며, Q Shop 잔액 변경 이벤트는 SG Economy에 반영한다. 정확한 트랜잭션/재접속 동작은 런타임 미확인.
- 물 증류기/필터/공급소 표식 블록 엔티티는 주변 청크가 틱할 때 서버 tick을 수행한다. 기계 수가 커지는 서버에서 전체 비용은 측정하지 않았다.

## 발견사항

### 12-1 / P2 / 신선수 고임 추적 데이터의 증가 상한과 처리 예산이 없음

- 위치: `FreshPoolDecayData`, `FreshWaterStagnator.scanTracked`
- 현재 동작: 관찰한 신선수 좌표가 차원 SavedData에 쌓인다. 주기적 처리 때 `keySet().toLongArray()`로 전체 키를 복사한 후 모든 추적 위치를 검사하고, 현재 미로드 위치는 유지한다.
- 플레이어 영향: 플레이 기간과 물 배치량이 늘면서 추적 좌표가 커지면 저장 파일 크기와 주기 스캔 비용도 증가할 수 있다. 풀 주변 추적을 제거하는 경로가 있는지는 확인했지만 항목별 정리/상한은 없다.
- 권장 조치: 프로파일링으로 실제 증가량과 주기 비용을 먼저 측정한다. 필요하면 좌표 대신 청크/풀 단위로 묶거나, 추적 항목 처리 예산과 청크 미로드 정리 정책을 둔다. 데이터 제거 시 고임 판정 의미가 바뀌지 않도록 세이브 이전 호환을 고려한다.
- 확신도: 코드 구조 높음, 사용자 체감 성능 영향은 미확인.

### 12-2 / P2 / 차원별 틱 이벤트에서 대기 청크 집합을 반복 훑음

- 위치: `WaterWorldHandler.onLevelTick`
- 현재 동작: 각 ServerLevel 틱마다 공유 대기 집합을 순회해 해당 차원의 청크 최대 2개를 찾는다. 여러 차원이 있고 대기 항목이 특정 차원에 몰리면 각 차원에서 반복 방문한다.
- 플레이어 영향: 매우 큰 구 청크 로드 대기열에서 추가 순회 비용이 발생할 수 있다. 변환 자체는 틱당 2청크로 제한되어 급격한 단일 틱 변환을 피한다.
- 권장 조치: 현장 TPS 문제가 확인될 때 차원별 큐로 분리하고, 미로드 청크 재시도/큐 크기를 관찰할 수 있는 카운터를 추가한다.
- 확신도: 보통.

### 12-3 / P2 / 통화 브리지는 접속자 수에 비례해 매 2초마다 실행

- 위치: `SgQShopCurrencyBridge.onPlayerTick`
- 현재 동작: 각 플레이어의 40틱마다 SG 잔액·Q Shop 잔액을 리플렉션 호출로 읽고, 다르면 Q Shop 값을 갱신한다. 로그인과 거래 변경 이벤트도 별도 처리한다.
- 플레이어 영향: 대규모 서버에서는 반복 호출 및 통화 API 내부 저장/동기화 비용이 접속자 수에 비례할 수 있다. 중복 거래/재접속 시 잔액 보존 정합성은 테스트하지 않았다.
- 권장 조치: 두 지갑이 실질적으로 하나라면 한 쪽을 정본으로 두고 UI 조회를 연결하는 방식과 주기 폴링의 비용을 비교한다. 현재 구조를 유지할 경우 서버 환경에서 동시 구매/판매, 차감 직후 저장, 재접속 후 잔액을 검증한다.
- 확신도: 코드 구조 높음, 병목/중복 결제 여부는 미확인.

### 12-4 / P1 / 서버·클라이언트 경계는 코드상 분리됐으나 dedicated server 실행 검증이 남음

- 현재 동작: 메인 모드는 공통 클래스, `RealismSurvivalClient`와 HUD는 client Dist로 분리되어 있고 payload는 client handler를 별도 등록한다. 외부 모드는 리플렉션/선택 의존성 가드를 사용하는 경로가 있다.
- 플레이어 영향: client 클래스의 잘못된 서버 로딩은 서버 기동 자체를 막을 수 있으며, 선택 모드 부재 시 링크 오류도 가능하다. 정적 구조만으로 실제 dedicated server 로딩은 보증되지 않는다.
- 권장 조치: 14번에서 기본 서버 프로필로 기동/접속/재접속을 확인한다. 선택 의존성 조합은 13번에서 확정한 프로필을 기준으로 검증한다.
- 확신도: 구조 분리는 높음, 실행 여부 미확인.

### 12-5 / P2 / 서버 권위 거래의 동시성·재접속 결과는 미확인

- 현재 동작: 상점 열기는 서버 상호작용에서 결정하고 통화 브리지도 서버 측 이벤트를 반영한다. Q Shop의 구매/판매 확정 패킷 내부 검증과 거래 한도의 동시성은 의존 모드 구현에 맡겨져 있다.
- 권장 조치: 14번에서 두 플레이어가 같은 상점을 동시에 이용하고, 한도가 1인 품목을 같은 틱에 구매하는 상황, 거래 직후 로그아웃/서버 종료 상황을 확인한다. 해당 동작은 현재 분석에서 결함으로 확정하지 않는다.
- 확신도: 코드 경계 보통, Q Shop 내부는 미확인.

## 후속 확인 계획

- 14번: dedicated server 기동, 플레이어 상태 저장·재접속·사망·차원 이동, 다인 상점 동시 거래, 공급소 생성과 NPC 중복 확인.
- 성능 프로파일링: 충분한 추적 물 좌표/기계/동시 플레이어가 있는 표본 월드에서 TPS와 저장 크기를 기록한다. 현재는 정적 후보만 식별했다.
- 저장 포맷을 바꾸는 수정은 기존 월드에서 load/save 후 재시작까지 확인한다.
