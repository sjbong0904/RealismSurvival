# 전수 검토 10 — NPC 상점·화폐·거래 UX

- 검토일: 2026-10-21
- 범위: 공급소 NPC 식별·진입, 구매/매입 목록, 금액·수량 표시, 화폐 브리지, 현재 Q Shop GUI 구조와 임의 아이템 판매/인벤토리형 GUI 구현 가능성
- 증거 수준: 코드·설정·의존 JAR의 정적 확인. 실제 게임 클릭/거래와 멀티플레이 동시 거래는 미실행.

## 요약 결론

현재 공급소는 NPC를 우클릭해 이용하는 흐름이 구현되어 있고, 일반 플레이어의 `qshop open supply_post...` 직접 명령을 차단한다. 판매(유저가 NPC에 물품을 판매하는 매입)는 설정 카탈로그의 품목만 고정 거래 항목으로 등록하는 방식이다. 기후·계절 가격 차등과 전문 상인의 매입 프리미엄은 구현되어 있다.

Q Shop 1.8.4 화면은 `ShopScreen` 기반의 자체 상점 화면이다. 구매/매입 목록, 거래 수량 조절과 확인 화면이 있어 현재 고정 상품 방식의 UX는 개선 여지가 있다. 그러나 Q Shop 거래 항목은 등록된 아이템·수량·가격이 사전에 정해져 있어, 플레이어가 임의 아이템을 투입하고 서버가 예상 금액을 산출하는 계산대 동작은 현재 구현되어 있지 않다. 이 기능은 별도 UI/서버 거래 로직이 필요하다. Q Shop의 현재 화면을 인벤토리 슬롯 중심 화면으로 바꾸는 것도 설정만으로 되는 변경은 아니며, 독립된 커스텀 화면 또는 Q Shop의 공개 확장 지점이 있는지 추가 구현 검토가 필요하다.

## 확인된 현행 흐름

1. `SupplyShopAccess.onEntityInteract`는 서버 측 메인 핸드 상호작용에서 `rs_shop` 태그와 Easy NPC 엔티티를 확인하고, 클릭한 NPC의 위치에서 기후를 판정한다. NPC 이름이 아니라 태그와 엔티티 종류가 실제 판별 기준이고, 분야는 엔티티 데이터에서 구한다.
2. `openSupplyShop`은 SG Economy 잔액을 Q Shop 지갑으로 밀어 넣은 뒤 `ShopManager.openShop`을 리플렉션으로 호출한다. 각 기후·분야 조합별 상점 ID가 별도로 만들어진다.
3. 명령어 차단은 `qshop open supply_post` 및 `qshop open supply_post_*` 형태의 세 번째 인자를 확인해 취소한다. 우클릭 경로에서 별도로 원거리 제한을 적용하는 코드는 없으나, 실제 클릭은 엔티티 상호작용 거리 안에서 발생한다. `nearSupplyMerchant`는 OP/크리에이티브 예외를 허용한다.
4. `SeasonalSupplyShop`은 계절 또는 시대 변화에 따라 Q Shop 등록 정보를 재생성한다. `SupplyStock.forMerchant`는 분야 판매품만 노출하면서 전체 공급 목록을 매입 목록으로 만들고, 전문 분야에 더 높은 매입가를 준다. 매입은 우선 카탈로그의 공급 품목에 한정된다.
5. Shop config의 각 거래는 품목/수량/가격/일일 플레이어 한도가 고정된 `BUY` 또는 `SELL` 항목이다. 상점 화면에서 거래 수량을 조절하고 확인하는 UI 요소가 의존 JAR에 존재한다.
6. 통화는 `coins`이며 SG Economy와 Q Shop 사이에 브리지가 있다. 문서상 플레이어는 골드 UI와 `/coins get`으로 잔액을 확인할 수 있다. 잔액 동기화 및 왕복 거래 정합성은 정적 코드 확인만으로 실제 동작을 보증하지 않는다.

## 발견사항

### 10-1 / P2 / NPC 전용 진입은 기본 경로에 구현됨

- 위치: `SupplyShopAccess.java`의 명령 이벤트 및 상호작용 처리
- 현재 동작: 직접 `qshop open supply_post...`를 차단하고 NPC 클릭으로 해당 NPC의 상점을 연다.
- 영향: 사용자가 원한 NPC 중심 접근과 일치한다. 다만 코드상 차단은 명령 문자열의 `qshop open` 패턴에 한정된다. 현재 Q Shop의 다른 공개 진입 경로가 있는지와 권한별 예외는 게임 안에서 확인하지 않았다.
- 권장 조치: 기본 UX는 적합. 배포 조합의 Q Shop 명령 별칭/FTB 연동 등 별도 진입 경로만 통합 회차에서 확인한다. NPC 이름은 표시용으로 유지하고, 중복 이름이 생겨도 분야 태그로 거래가 결정되도록 한다.
- 확신도: 코드 경로 높음, 대체 진입 경로는 미확인.

### 10-2 / P1 / 임의 아이템 매입은 현재 고정 카탈로그 구조로는 불가능

- 위치: `supply_shop_seasons.json`, `SeasonalSupplyShop.rebuildShop`, `SupplyStock.forMerchant`
- 현재 동작: 시즌 카탈로그에 정의된 품목만 매입 거래로 등록된다. 모든 아이템에 대한 일반 매입이나 인벤토리 투입 계산대가 아니다.
- 플레이어 영향: 목록에 없는 모드 아이템은 NPC에 팔 수 없다. 반대로 단순히 “모든 아이템”을 허용하면 제작 부산물·재생 가능한 아이템·장비 NBT/인챈트 가치·복제 가능한 아이템이 경제 우회가 될 수 있다.
- 권장 조치: 우선 범위를 두 단계로 나눈다. 단기에는 태그/분류 기반 허용 품목을 늘리고 아이템별 기본가·기후/계절 배율·거래 한도·금지 태그를 정한다. 장기에는 판매 칸에 실제 아이템을 넣고 서버가 유효성 및 단가를 계산해 견적을 표시한 뒤 확정 거래하는 전용 계산대 UI를 검토한다. 견적 수령 후 인벤토리 변경, NBT, 수량 변경, 가격 갱신, 재접속으로 이득을 얻지 못하게 서버가 거래 확정 시점에 다시 검증해야 한다.
- 확신도: 높음.

### 10-3 / P2 / Q Shop GUI는 현재 고정 거래 선택형이며 인벤토리형이 아님

- 위치: `qshop-neoforge-26.1.2-1.8.4.jar` 내 `ShopScreen`, `QShopScreen`, `ShopEntry`
- 확인: 화면 클래스에 탭·거래 그리드·거래 수량 입력/슬라이더·확인 버튼이 존재한다. Q Shop 설정의 `ShopEntry`도 고정 아이템/수량/가격 및 지급/수령 목록 구조다. 일반적인 Minecraft `AbstractContainerScreen`+슬롯 컨테이너처럼 플레이어 아이템을 직접 상점 슬롯에 옮기는 구조는 공개 클래스 형태에서 확인되지 않았다.
- 권장 조치: 현 GUI를 활용한다면 첫 탭에 “구매 / 판매 안내”와 분류 탭을 두고, 검색·수량 조절·가격 툴팁을 정리하는 개선이 현실적이다. 진짜 계산대형 UX가 우선이면 Q Shop 화면에 억지로 끼우기보다 커스텀 서버 검증 UI를 별도 설계한다. Q Shop 공개 API로 화면 확장이 가능한지는 JAR 서명/문서가 더 필요하다.
- 확신도: 현재 데이터 모델과 화면 형태는 높음, 확장 API 부재는 미확인.

### 10-4 / P2 / 가격은 상세 화면 진입 전부터 더 잘 보여줄 필요

- 위치: 시즌 카탈로그와 Q Shop 고정 거래 항목
- 현재 동작: 매입가가 기후·계절·상인 분야에 따라 달라질 수 있으나, 처음 상점에 들어가기 전 예상 단가/분야 프리미엄을 안내하는 흐름은 문서·데이터에서 확인되지 않았다. 거래 항목의 가격 툴팁은 Q Shop 화면에 구현된 것으로 보이나 게임 내 가독성은 미확인이다.
- 권장 조치: 상점 첫 화면에 통화 이름과 “전문 상인 매입가 우대”, 수량별 총액, 일일 한도를 표시한다. 매입 확정 전 총액을 보여주고, 현재 기후/계절 때문에 가격이 달라진 경우 이를 화면에 명시한다.
- 확신도: 보통.

### 10-5 / P2 / 문서의 상점 구조 안내에 예외와 용어를 보완할 필요

- 위치: `docs/SHOP_SUPPLY_POST.md`
- 현재 동작: 플레이어는 “매입” 대신 일부 문장에서 판매 관점으로 읽을 수 있고, 크리에이티브/OP는 근처 NPC 검사에서 예외다. NPC 이름으로 분야를 구분할 수 있다는 사용자의 설명과 코드상 태그/분야 판정 기준이 문서에서 구별되지 않는다.
- 권장 조치: UI에서는 “구매: NPC 물품을 산다 / 판매: 내 물품을 NPC에 판다”로 통일한다. 상인 이름은 분야 식별용, 거래 권한은 NPC 태그 및 내부 분야 데이터로 결정된다고 정리한다.
- 확신도: 높음.

## 제안 UX 흐름

**현 Q Shop 유지형**: NPC 클릭 → 첫 화면에서 구매/판매 탭 선택 → 카테고리 선택 → 상품 선택 → 단가·현재 잔액·거래 한도 확인 → 수량 조절 → 총액 확인 → 거래 확정. 판매 목록은 “내 인벤토리에 있는 수량”보다 거래 가능한 수량과 예상 총액을 분명히 보여준다.

**계산대형**: NPC 클릭 → 판매 칸에 아이템/수량 배치 → 허용 여부와 단가·총액 표시 → 플레이어가 확정 → 서버가 현재 아이템 스택/가격/잔액을 다시 검사하고 한 번에 교환. 무가치·금지 아이템, 손상도·NBT 처리, 중첩 불가 아이템, 가격 변동, 아이템 회수와 거래 취소를 명세해야 한다.

현재 팩에는 첫 번째 방식이 낮은 변경량으로 적용 가능하다. 두 번째는 사용자가 제안한 UX에 더 가깝지만, 서버 권위 거래 로직과 경제 기준을 새로 구현해야 하는 별도 기능이다. “모든 아이템 허용”은 바로 전면 적용하기보다 허용 태그와 가격 정책을 먼저 확정할 필요가 있다.

## 미확인·후속 확인

- 상점 화면의 가격 툴팁, 수량 조절, 거래 취소가 실제 클라이언트에서 자연스러운지.
- SG Economy ↔ Q Shop 지갑 잔액이 구매·판매·재접속·서버 환경에서 정확히 동기화되는지.
- Q Shop 공개 확장 API가 인벤토리형 화면 또는 사용자 정의 거래 콜백을 지원하는지.
- 명령어 우회는 `qshop open` 외 진입 경로와 OP/크리에이티브 조건을 포함해 12·14번에서 확인한다.

## 후속 회차 연결

- 11번: 가격·거래 상태가 한국어 UI에서 발견 가능하고 이해 가능한지 확인.
- 12번: 지갑 동기화·동시 거래·권한 검증 확인.
- 14번: NPC 실제 클릭부터 거래 완료까지 통합 시나리오 확인.
- 수정 우선 검토: 먼저 고정 거래 UI의 구매/판매 분리와 예상 총액 가독성을 개선하고, 임의 아이템 매입 계산대는 별도 구현안으로 비용·경제 악용 방지를 검토한다.
